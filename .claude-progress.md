## 2026-09-03 — Entry flows: recipes and ingredients, for a hand on a keyboard

**Brief**: think like a designer for a chef or data-entry person. Easy to
start, easy to end, not over-clicked. Look "very carefully" at add-dish and
add-ingredient.

**What the audit found** (walked in the running app, not read):
- The Ingredients entry row was already the right pattern — Tab across, Enter
  commits, row clears and refocuses, duplicates caught before they exist.
- Recipe lines had **no typed quantity anywhere**. A picked ingredient started
  at 1 kg and the only control was a −/+ stepper on the stored gram figure in
  steps of 50/10/5/1 — ~30 presses to reach 250 g. Deliberate for a wet finger
  on a tablet (A13); wrong for a hand on a keyboard entering a recipe.
- The Add-line drawer printed ₹ on an AED account: `lib/picker.ts` formatted
  its rate with `ORG.currencySymbol` — the demo fixture from `lib/data.ts`.
- Every `Sheet` stole focus on parent re-render: `[open, onClose]` as effect
  deps, inline `onClose` recreated each render, `panel.focus()` inside.

**What was built**:
- The drawer asks "How much?" at pick time. Type "250 g", Enter — the line
  lands, the drawer stays open, focus returns to search. Enter on an empty
  field is the old one-press 1 kg. `addComponent` takes an amount; a unit
  from the wrong family ("250 ml" of a thing bought by weight) is refused in
  words, never costed on a guess. 4 tests.
- A typed quantity beside the stepper on every expanded line. Beside, never
  instead: the stepper stays for tablets.
- "500 g" / "2 l" typed into the ingredient row's Pack qty sets quantity and
  unit (grams and millilitres convert to a fraction of the kg/l pack).
- Picker rows carry a figure; the screen formats it in the currency in force.
- `Sheet` holds `onClose` in a ref and focuses once, on opening.

**Decisions**: never remove the stepper; add typing beside it. Parse typed
quantities with `core/loose.ts`, not a second parser. Gulf currency codes are
prefix with a space ("AED 83").

**Verified on the production build on :3000**: pick → focus in the field →
"250 g" Enter → 20 lines, last 250 → focus back in search → Escape closes.
Nothing saved.

## 2026-09-11 — the payment callback

**What was asked**: build the webhook. The keys are in and authenticate
(`rzp_test_Tai…`, test mode).

**The bug it closes**: a payment was confirmed by exactly one thing — the

callback needs a session-less client, which means the service_role key, which

changed, in writing, with the reason. It is read by one module, imported by
one other, imported by one route; nothing a person looks at reaches it.

  secret, and `paymentFromWebhook` parsing a stranger's JSON off `unknown`.
  An unset secret refuses rather than signing with an empty key.
- `lib/settle.ts` — claim, check, apply. Amount compared exactly, before the
  claim, because Razorpay allows part-paying an order and a partial capture
  arrives looking normal.
- `lib/plan.ts` — `startsAt` pulled out of `activateSubscription`, so the two
  paths cannot disagree about when a stretch begins.
- `app/api/razorpay/webhook/route.ts` — 200 to everything understood
  (including ignored events and already-applied payments, because a non-2xx
  means a day of redelivery); 500 only where a retry helps.

**The honest gap**: two statements, no transaction. If the claim lands and the
plan then fails to switch on, the claim is rolled back and the caller answers
500 so the provider retries onto a clean order. If the rollback itself fails
it is logged with the order id as a human repair. Tested.

**Verified**: 1029 tests, typecheck cold-cache clean, `next build` registers

## 2026-09-11 — the rest of the payment flow, audited

**Swept and clean**: every server action that redirects is in plans, setup,

## 2026-09-12 — closing an account, which was a sentence and is now a thing

The privacy page has promised deletion since before there was any way to do
it. What existed was an address to write to — a promise kept by hand, on
somebody's good day, and not at all on a bad one.

**`lib/erase.ts`** — needs the admin key and not for convenience: there is no
delete policy on `organizations` (row security grants an owner select and
update and nothing else), so an owner genuinely cannot remove their own book
through their own session, and `auth.users` is not a table the data API will
touch at all.

**The finding that made this worth doing carefully.** Twelve tables cascade
from `organizations`. Two do not:

- `app_errors.org_id` is ON DELETE SET NULL, deliberately and correctly — a
  crash record outlives the account, and the table is built to hold no
  payload: a message and a route, never a rate, a dish name or an address.
- `mail_outbox.thread_id` is ALSO ON DELETE SET NULL, and **that one is a
  leak**. The row carries `to_email` and the full body of what was written.
  Cascade the threads away first and the outbox keeps a person's address and
  their whole support conversation, orphaned, with nothing left pointing at
  them to say whose it was — exactly the copy the page promises not to keep.

So the outbox is cleared BEFORE the org, while the threads still exist to find
it by. `lib/erase.test.ts` asserts that order, and was proved by swapping the
two statements and watching the conversation survive.

**Sign-ins are removed last**, and only for somebody this was the last book
of. Today that is always all of them — one owner, no invitations — written as
a check rather than an assumption because the day it stops being true, closing
one kitchen would lock a person out of another, and that arrives as somebody
unable to sign in with no idea why.

**Three guards, three different mistakes**: `requireRole('team')` for a
manager, the typed business name for an accidental press, and
`serviceKeyPresent()` so the action can never report a deletion it did not do.
Case and surrounding space are forgiven — this is a guard, not a password.

**No undo, and none offered.** A seven-day grace period needs something to run
on the seventh day and this product has no scheduler. The privacy page and its
figure were rewritten to say immediate, because a delay nothing is scheduled

account are both gone, so a gate would answer the one person it was written
